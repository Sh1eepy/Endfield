# RAG 技术概览

> 当前统一架构见 [`KNOWLEDGE_SYSTEM_ARCHITECTURE.md`](../KNOWLEDGE_SYSTEM_ARCHITECTURE.md)。这份文档只保留 RAG 专项细节。

## 数据怎么进入索引

```text
WIKI 原始数据
  → build_kb_all.py：整理成 22 类 JSONL/Markdown
  → build_operator_details.py：提取干员详情和多语种语音
  → build_rag.py：切片并加“分类 + 名称”前缀
  → Chroma 向量索引 + 分类 BM25 分片 + chunks.json manifest
```

切片优先使用条目的 `sections`。如果 `sections` 为空，就回退到 `full_text`；如果 sections 只覆盖部分正文，
会再加入未覆盖的描述/其他内容。干员“语音记录”章节的中文台词以独立 `干员语音` 记录进入索引。
游戏专名会进入 jieba 自定义词典，名称前缀同时帮助关键词和向量检索。

增量更新按正文、sections 与索引策略版本的组合哈希工作：只更新变化条目的向量，只重建变化分类的
BM25；切分代码升级也会触发更新。Chroma 分批写入，构建结束核对 manifest、Chroma 和 BM25 是否一致。

## 查询怎么检索

第一层混合检索包含：

- 名称检索：优先找条目本身；
- BM25：适合专名、数值和精确词；
- 向量检索：适合自然语言和语义近似；
- RRF：合并三路排名，默认返回前 5 条。

确定性配方/设备与枚举优先直查；其他问题用一次受约束 LLM 输出语义检索计划（问题类型、核心动词、
关键词、最多 3 条子查询和白名单路由），再加入实体直取、mention 和全文关键词检索。规划器不能回答事实。

当前不使用 reranker。现有 71 条严格检索集已经达到 Recall@5=100%、MRR=97.3%，评测集还不足以
证明增加 reranker 的延迟和复杂度值得。先扩充真实困难问题，再做决定。

## 长文档怎么处理

实体直取虽然能拿到全文，但不能把全文无限塞给模型。`focus_long_context()` 会从全文各处挑选与查询实体、
关系词和问题实词相关的窗口，不再固定截取开头。默认每个来源最多 1800 字、最多 7 个窗口。

已有回归用例覆盖答案在 1500 字之后、复合问题证据分散在不同位置。仍需继续补跨段指代和超长表格案例。

## 答案边界

- LLM 只能根据检索资料回答，并保留来源；
- 普通检索分数过低会拒答；
- direct、mention、keyword 等确定性命中不会被向量阈值误拒；
- LLM 未配置或调用失败时安全降级；
- 图谱没有路径只表示图里没证据，问答会继续回退文本检索。

检索命中不等于答案正确。最终还要检查完整性、忠实度、引用和拒答是否合理。

## 监控与评测

| 层级 | 工具 | 用途 |
|---|---|---|
| 索引 | `rag_audit.py` | 核对 KB、manifest、Chroma、BM25 |
| 健康 | `/api/health/deep` | 检查索引、数据哈希、mention 和 LLM 配置 |
| 运行 | `/api/metrics` | 请求、错误、路由、空结果、降级、总延迟 |
| 检索 | `eval_retrieval.py` | Recall@K、MRR、Precision@K |
| 路由 | `eval_pipeline.py` | 意图和实际路由 |
| 答案 | `eval_answers.py` | 必要事实、引用、拒答，可选 LLM judge |
| 总门禁 | `quality_gate.py` | 指标低于阈值时失败 |

当前监控是单进程内存指标，重启会归零，也没有多实例聚合和主动报警。正式生产可接
Prometheus/OpenTelemetry，但不影响本地功能。

## 当前结果与限制

- 分类知识库 1958 条 + 中文干员语音 2373 条；RAG 共 7319 chunks；
- 检索集：71 条，Recall@5=100%、MRR=97.3%；
- 路由集：25 条，当前准确率 92%；
- 答案集：只有 6 条，能验证链路，不能代表生产正确率。

下一步最有价值的是把真实失败问题沉淀成 20～50 条困难集，按“数据缺失、第一轮证据不全、关系错误、
生成错误、应该拒答”分类。只有第一轮证据不全占主要比例时，才考虑增加一次受限补检索循环。
