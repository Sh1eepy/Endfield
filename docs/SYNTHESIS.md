# 配方合成树

## 职责与技术选型

配方树是确定性领域能力。数据来自 `output/recipes.json`，索引工具位于 `scripts/recipe_index.py`，服务入口和递归树构建位于 `scripts/api_server.py`。Web 使用 React 递归 SVG，小程序使用 Canvas；两端共享响应数据与业务不变量，各自实现渲染和手势。

选择结构化配方而非 RAG，是因为原料、数量、设备和耗时必须精确；选择 SVG/Canvas，是为了直接控制节点、连线、缩放与移动端交互，无需维护已弃用的 D3 依赖。

## 业务不变量

1. 叶子只能是清水、惰气、息壤气、无产出配方矿物或种子类基础资源；
2. 排除自循环，每个物品最多展示 2 个配方；
3. 当前路径再次出现同一物品时剪枝，最大深度为 10；
4. 同名歧义返回候选，不自行选择；
5. 设备返回配方卡；无配方物品回退知识库详情；
6. 配方提取保留完整真实记录，展示规则不反向清洗事实数据。

## 测试问题与对策

- 小样例容易漏掉真实数据中的循环和异常配方，因此测试必须遍历全部真实配方并检查叶子、深度和分支数；
- 改布局可能让宽度或 SVG 单位爆炸，需覆盖深树、双配方、窄屏和容器 resize；
- 节点名称点击、折叠、缩放容易在视觉重构中回退，Web 组件测试与静态契约测试共同保护；
- Canvas 与 SVG 不共享渲染实现，发布前需分别做浏览器交互和微信真机验收。

主要验证命令见 [TESTING.md](TESTING.md)。

## 扩展接口

- API 可逐步增加稳定 `item_id` 查询，同时保留名称兼容层；
- 将树布局抽成只接收纯数据、输出坐标的模块，供 SVG、Canvas 与导出功能复用；
- 可在响应中增加配方选择策略、节点状态和 schema 版本，但不得改变默认最多两配方规则；
- 若将来支持用户自定义目标数量，应在结构化层计算数量传播，避免由展示层或 LLM 推算。
