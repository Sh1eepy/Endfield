# 检索与问答设计（含知识图谱）

> 更新日期：2026-09-14。本文合并原“RAG 问答设计”与“GraphRAG 专项设计”，说明知识问答的检索编排、切分索引、召回融合、答案边界、流式输出与知识图谱。
> 整体模块关系见 [ARCHITECTURE.md](ARCHITECTURE.md)，接口契约见 [API.md](API.md)，验证矩阵见 [TESTING.md](TESTING.md)。配方树使用独立结构化数据，不由 RAG 推测。

## 1. 目标与优先级

本系统按“事实准确和证据可追溯 → 失败可见和稳定可复现 → 答案完整 → 延迟成本受控 → 表达自然”排序。
困难问题多花一次检索或模型调用是合理的，但额外步骤必须带来可测收益，并有超时、次数上限、日志和降级路径。

三套能力各管一段，互不替代：

| 能力 | 数据 | 擅长 | 不擅长 |
|---|---|---|---|
| 结构化直查 | `recipes.json`、分类清单 | 配方、设备、确定性枚举 | 性格、剧情概括 |
| RAG | chunks、全文、BM25、向量、名称、mention | 描述、数值、档案、剧情、模糊问题 | 保证关系路径完整、穷举关系 |
| 知识图谱 | `output/knowledge_graph/graph.db` | 明确关系、正反问法、1～3 跳路径 | 未建模观点、长文本概括 |

知识图谱不是 RAG 的替代品。GraphRAG 是图检索和文本检索协作的系统形态；本项目实现轻量、可审计的 GraphRAG，
不把所有文本都永久转成模型猜测的边。

## 2. 检索与生成流程

```text
query → 确定性强规则优先
  ├─ 配方/设备：recipes 直查
  ├─ 枚举：分类/主题过滤
  └─ 其他：一次受约束语义检索规划
       ├─ 明确人物关系/多跳：图检索 + 原文证据
       └─ 事实/对象偏好/开放问题：RAG + 全文关键词 + mention
→ 图未命中回退 RAG
→ 复合/主观关系：事实图边 + 原文证据窗口
→ 证据阈值与覆盖检查 → LLM 据证生成或拒答
```

- 精确事实先结构化；能用配方表、分类或图边确定的内容不让 LLM 猜。
- 描述性内容回原文；性格、剧情、态度由 RAG 找证据，模型仅作有边界归纳。
- 语义规划器只输出问题类型、主题词、子查询和白名单路由，不允许输出事实答案；例如“喜欢吃什么”识别为饮食偏好，而不是因为“喜欢”二字误送到人物关系路线。
- 事实与解释分开。例如“狼卫的妹妹是谁，她可爱吗”：图谱回答洛茜，原文支持主观说明；主观证据不足不能连带拒绝已经确定的姓名。
- 关系问题按需直接查图；图不足再走 RAG/mention，而不是机械混合图分和向量分。
- 态度等解释性关系证据必须同时命中具体主体与关系对象/线索；每个来源只保留最高分窗口，避免泛称或相邻片段挤满上下文。
- direct、graph、mention、keyword 和普通 RAG 命中保留类型标志，人工确认通道优先。

### 2.1 当前是不是 Agent

不是完整 Agent，而是**确定性编排管线 + 可选 LLM 子步骤**：它没有通用工具协议、观察后的重新规划、工作记忆或开放循环。

| 路径 | 典型 LLM 次数 | 说明 |
|---|---:|---|
| 配方/设备直查且不生成 | 0 | 完全结构化 |
| 结构化结果文本整理 | 0～1 | 仅需要自然语言时生成 |
| 普通开放 RAG | 通常 2 | 语义检索规划一次，最终回答一次 |
| 低置信开放问题 | 通常 2 | 规划同时承担意图理解和查询改写，不再重复调用分类器 |
| 图关系且路径明确 | 1～2 | 可规则直达；需要消歧时先规划，最后生成一次 |

失败或未配置 LLM 时会规则降级，因此实际次数可能更少。

## 3. 切分与索引

```text
官方 WIKI 块式数据
  ├─ build_kb_all.py → 22 类 JSONL/Markdown（full_text、sections、来源标识）
  │    ├─ build_rag.py → contextual chunks → Chroma + 分类 BM25 + manifest
  │    ├─ mention_index → “谁的原文提到了实体 X”反查
  │    └─ build_knowledge_graph.py → 实体、关系、证据、来源哈希 → SQLite 图谱
  ├─ build_operator_details.py → 干员详情 → 中文语音台词进入 build_rag.py
  └─ recipe_extract.py → 真实配方结构 → recipes.json
```

### 3.1 切片规则

- 正常条目按 `sections` 切；长 section 按自然边界再分块，短内容合并，避免标题碎片。
- `sections` 为空但 `full_text` 有内容时回退切全文。此前 53 个长条目产生 0 chunk，现已修复。
- `sections` 非空时仍对照 `full_text`，把未覆盖的描述、档案“其他内容”等作为全文补充分块。
- 干员详情中的中文语音台词以稳定 audio id 独立入库；多语种翻译和 EP 演职员信息不重复进入中文索引。
- chunk 加 `【分类】名称：条目名` 前缀，使专名同时进入 BM25 和 embedding。
- jieba 加载项目专名词典，避免“重息壤”等被通用分词拆散。

### 3.2 索引一致性与增量规则

- manifest 保存条目哈希和 chunk 键；哈希包含正文、sections 与索引策略版本，切分算法升级也会触发更新。
- Chroma 按批写入；增量构建按完整新旧 chunk 集删除遗留向量，只更新变化条目及分类 BM25，并校验三套索引一致性。
- embedding 模型变化要求新输出目录，防止不同向量混在同一 collection；BM25 与 manifest 通过同目录临时文件原子替换。
- mention 反查缓存保存规范化知识源指纹；文件存在但格式旧或指纹不符时自动重建，审计不再把“存在”误判为“新鲜”。

## 4. 召回与融合

| 环节 | 选型 | 理由 |
|---|---|---|
| 向量模型 | `BAAI/bge-small-zh-v1.5`（CPU、离线，`rag_config.py` 是唯一配置来源） | 语料是中文游戏百科；镜像需要离线运行、无按量费用；体积小可在单机 CPU 上承担构建与查询 |
| 向量库 | ChromaDB `PersistentClient`，集合固定 `hnsw:space=cosine` | 8 千余 chunk 的单机规模，需要零运维、可删除重建、可审计 |
| 关键词检索 | rank-bm25，按分类分片持久化 | 专名与短名称（“负山”“诀”）必须字面命中；分片使增量只重建变更分类 |
| 融合 | RRF（`RRF_K=60`）后取 `FINAL_TOP_K=5` | 不同检索器分数不可比，排名融合更稳定；参数集中一处便于消融实验 |
| 分词 | jieba + 项目专名词典 | 避免“重息壤”“向心之引”被通用词典拆碎导致 BM25 失配 |
| 生成 | OpenAI 兼容在线模型，`GEN_ANSWER_MAX_TOKENS=1600`，截断最多续写一次 | 生成只能基于检索证据；模型可换，但 Prompt、预算与评测清单必须同步版本 |

未采用：在线 embedding API（离线与费用约束）、更大的中文向量模型（CPU/内存成本，需评测证明收益）、单一向量检索（专名召回不足）、reranker 与补检索循环（须先有困难集证据，见第 10 节）。

### 4.1 召回侧优化

- 名称规范化与分词在索引加载时预计算，向量 chunk ID 映射常驻内存；
- 用户明确点名和常见后缀省略的高置信来源在最终 Top-K 中得到保护；
- 原问题、实体加权查询和规划器子查询先去重；实体已命中时不再无条件重复执行完整混合检索；
- 同一来源的多个 chunk 有界合并，保留后续章节证据，同时避免一个来源占满上下文；
- 2026-09-08 同机 warm 离线探针从约 796–813 ms 降至约 24–25 ms；该结果不含在线规划和生成，不能外推为线上总延迟。

## 5. 答案边界与拒答

- LLM 只能根据检索资料回答，并保留来源（`[来源N]`）；
- 普通检索首条向量相似度低于 `GENERATION_MIN_VECTOR_SIM=0.45` 会在生成前拒答；实体直取，或命中片段中含关键词/mention/直取/关系证据等人工确认上下文时不受该阈值误拒。该阈值在 `rag_config.py` 集中定义并写入评测 manifest，2026-09-14 由 0.30 校准而来（校准的前后对照见 [测试与质量](TESTING.md)）；
- LLM 未配置或调用失败时安全降级（返回检索片段而非报错）；
- 实体解析优先完整名称并保留稳定 `item_id`，避免把“重息壤”解析成“息壤”；
- 图谱没有路径只表示图里没证据，问答继续回退文本检索，不能断言“关系不存在”；
- 检索命中不等于答案正确：最终仍要检查完整性、忠实度、引用和拒答是否合理。

### 5.1 截断与上下文预算

旧版 `gen_answer()` 每来源固定取开头 1500 字，答案在档案后段时永远不可见；现由 `focus_long_context()` 按查询评分选段。

| 限制 | 目的 | 风险与处理 |
|---|---|---|
| 每来源 1800 字、最多 7 个窗口 | 控制 prompt、避免碎片过多 | 遍历全文句/行，以查询实体、关系词、评价词和实词评分，从不同位置选窗口，先为每个查询维度选最佳窗口；查询驱动选段，不盲截开头，远端答案有回归测试 |
| 默认生成 top-k=5 | 控制噪声 | 解释性复合关系至少 8；困难集决定是否调整 |
| 图路径最多 3 跳 | 控制路径爆炸 | 超限回退文本，不能解释为关系不存在 |
| 图边证据 500 字 | 明确句通常足够 | 保留来源；未来超长表格应改存 span/块 ID |
| 枚举结果 | 完整性优先 | API 返回完整 names，并确定性生成完整清单，不经过 LLM/token 截断 |
| 回答生成 | 完整结束优先 | 常规预算 1600 tokens；模型明确报长度截断时自动续写一次，二次截断显式失败 |
| 前端摘要 260 字 | 仅预览 | 不影响后端生成 |
| API 媒体摘要 300/800 字 | 仅详情预览 | 不进入 `/api/ask` 生成上下文 |

剩余风险：词面窗口对远距离指代仍可能漏证；图证据 500 字不是原文 span。评测应加入答案在末尾、跨段指代、双子问分散在首尾的样本。

## 6. 流式输出与启动预热

- `POST /api/ask/stream`（SSE）与 `/api/ask` 共用同一路由/检索逻辑，只把答案生成改为增量推送：事件顺序 `phase（受理/检索中）→ meta（意图 + 来源先亮）→ delta×N（逐段文字）→ done（完整结果）`。`prepare_generation()` 让流式/非流式共用同一份拒答判断与上下文组装，`done` 与整包返回体逐字等价。
- 流式改善的是**感知延迟**（等待从“整段生成完才显示”变成“来源先亮、文字持续流动”），不减少最后一个字的完成时间；首字前的主要等待来自语义规划那次 LLM 调用，这是后续“已知实体直问跳过规划”优化的目标（须由门禁证明收益）。
- 网页端默认走流式接口（来源 chips 先于文字出现）；小程序与评测/门禁继续使用旧 `/api/ask`；旧后端没有流式端点时网页自动回退整包请求。
- 流式模型只有明确 `finish_reason=stop` 才完整结束；`length` 触发最多一次续写，普通 EOF 或未知原因进入错误路径。
- `LLM_TOTAL_TIMEOUT` 是一次 `chat`/`chat_json`/`chat_stream` 操作及其重试、续写的总预算，不是整道问题从规划到回答的统一 deadline。
- 启动预热：`start_server.py`（Dockerfile/Compose 入口）单进程默认预加载 embedding 模型与 RAG/配方索引，把冷启动从首个问答请求移进健康检查 `start_period`；内存极紧可用 `RAG_PREWARM=0` 关闭退回惰性加载。
- Nginx 模板（`deploy/nginx/endfield.conf`）已为 `/api/ask/stream` 关闭 `proxy_buffering` 并把读超时放宽到 300s；部署/更新线上 Nginx 需同步，否则 SSE 会被代理攒批、失去逐字效果。

## 7. 知识图谱

图谱解决的是 RAG 不擅长的部分——明确关系和路径：

```text
关系问题 → 图检索 → 路径和证据 → LLM 整理
图未命中 → 文本 RAG 回退
主观问题 → 原文证据，不把模型判断写成事实边
```

### 7.1 建模与证据要求

- 实体覆盖人物、任务、地点、组织、物品、设备、配方；名称、类型和来源可追溯。
- 关系包含隶属、任务参与者、任务地点、前后置、生产、消耗、推荐、获取、明确亲属和管理关系；只从结构化字段、配方结构或原文明确句式建立。
- 每条边保存来源条目、原文片段、置信度、提取方法和审查状态。
- 别名只保存审定过的名称映射，不把模糊相似词自动当别名。
- 亲属、隶属、参与任务、生产/消耗等事实可入图；“喜欢、可爱、性格如何”等解释不固化成边。
- 同场出现仅可作为文本线索，不能自动等价为事实关系。

### 7.2 构建与增量更新

`build_knowledge_graph.py` 从规范化知识库、干员详情和配方数据中按白名单规则提取关系。
当前产物位于 `output/knowledge_graph/graph.db`，为 2,405 个实体、10,076 条关系、2,229 个来源。

```powershell
python scripts/build_knowledge_graph.py
python scripts/build_knowledge_graph.py --incremental
```

- 来源指纹覆盖结构化章节、干员详情与规则 schema；来源变化后先删除该来源旧边再重新提取。
- 来源下线时删除对应实体，并把仍引用该实体的来源纳入重建，避免悬挂关系和幽灵实体。
- 实体写入使用 UPSERT，避免替换实体时删除被引用关系；运行时查询以 SQLite 只读模式打开。
- 自动审查可逆问法，例如“庄方宜是不是武陵领袖”和“武陵领袖是谁”必须落到同一证据。

### 7.3 查询规则

- 明确关系词或两个实体触发图查询；默认最多 3 跳，避免路径爆炸。
- 正向、反向和是非问应该返回同一证据。
- 图中无路径不能解释成关系不存在；“关系怎么样、是否喜欢、性格如何”回到原文证据。
- 例如“武陵的领袖是谁”会查管理关系；回答仍保留原文“管代/管理负责人”的含义，不扩大成没有证据的政治职务。
- “陈千语和诀的关系”可通过共同任务路径回答，同时把任务原文交给模型说明。

### 7.4 审查与错误治理

- 用 `graph_audit.py`、`eval_graph.py`、`audit_relation_queries.py` 和 `quality_gate.py` 检查悬空端点、缺失来源、非法自环、关系证据、固定问题路径，以及各关系类型的正向、反向、是非问。
- 每条边必须能定位来源和证据；构建器用白名单规则，不允许 LLM 把猜测直接写入正式图。
- 错误应修正规则并按来源重建，不手改一条不可复现的数据库记录。
- 现有数字只说明规则和固定数据没有回退；新增剧情关系前仍应补人工金标，尤其是别名、冲突、三跳和拒答。

## 8. 质量门禁与监控

- 检索：Recall@K、MRR、Precision@K，按问题类型分组。
- 图谱：实体/边数、孤立实体、悬空端点、来源缺失、正反问法一致率、关系评测。
- 端到端：忠实度、完整性、引用正确性、拒答正确率；检索 100% 不等于问答 100%。
- 运行：延迟、错误率、路由分布、空检索率、LLM 降级率、阶段耗时与调用次数。
- 变更：构建一致性、自动测试、检索评测、图评测、关系审查；指标回退阻止发布。
- 人工：高风险关系、困难复合问题和失败样本回看原文；LLM-as-judge 只能辅助金标。

| 层级 | 工具 | 用途 |
|---|---|---|
| 索引 | `rag_audit.py` | 核对 KB、manifest、Chroma、BM25 一致性 |
| 健康 | `/api/health/deep` | 检查索引、数据哈希、mention 和 LLM 配置 |
| 运行 | `/api/metrics` | 请求、错误、路由、空结果、降级、总延迟 |
| 检索 | `eval_retrieval.py` | Recall@K、MRR、Precision@K |
| 图谱 | `graph_audit.py`、`eval_graph.py`、`audit_relation_queries.py` | 悬空端点、来源缺失、正反问法一致率、固定问题路径 |
| 路由 | `eval_pipeline.py` | 意图和实际路由 |
| 答案 | `eval_answers.py` | 必要事实、引用、拒答，可选 LLM judge |
| 总门禁 | `quality_gate.py` | 指标低于阈值时失败；`--require-versioned-results` 追加 manifest 版本要求 |

当前监控是单进程内存指标（重启归零），无多实例聚合和主动报警；正式生产可接 Prometheus/OpenTelemetry，不影响本地功能。

### 8.1 维护顺序

1. 更新并提取规范化知识库；
2. 增量构建 RAG，验证 manifest/BM25/Chroma 一致；
3. 增量构建图谱并做关系审查；
4. 跑单测、检索评测、图评测和质量门禁；
5. 将失败归因到源数据、切片/召回、关系规则或生成；
6. 只有评测证明需要时才加 reranker、补检索循环或更大模型。

## 9. 当前结果与限制

- 分类知识库 2,229 条 + 中文干员语音 2,535 条；RAG 共 8,300 chunks。
- 检索集 71 条：Recall@5=98.59%、MRR=97.89%、Precision@5=45.35%。
- 路由集 25 条，准确率 92%。
- 答案集：当前 manifest 下在线评测 6 条，拒答正确率、必要事实覆盖、引用/结构化溯源均为 100%，来源重合 66.67%；只验证固定链路，不能代表生产正确率。

## 10. 扩展边界

- 边证据从固定文本扩为原文 `span` 或块 ID，以支持精确引用；当前单来源路径保留 `item_id`，多来源路径尚不能直接打开原文。
- 图构建规则带独立版本和迁移脚本，升级后可按来源重建；别名只经人工审定后进入 `graph_aliases.json`。
- 多实例可将 SQLite 替换为图数据库，但必须保留来源、证据、规则版本和确定性审计语义。
- 新关系类型上线前必须加入正向、反向、是非问和无证据拒答样本。
- 补检索循环只在困难评测证明“第一轮证据不完整”是主要剩余错误时引入：最多一次，从白名单（graph、RAG、entity direct、mention/keyword、recipe、枚举）选择，带 JSON 参数校验、总超时、完整 trace，不写长期记忆，不允许模型修改图谱；门槛是困难集端到端正确率显著提升且拒答正确率不下降。
- reranker 先加入 hard negatives，只有首位排序和引用明显改善时启用；参数消融在固定版本清单上比较 BM25/向量 top-n、RRF k 与最终 top-k。
- 评测侧：从已批准反馈中人工挑选代表性样本，另建 holdout/challenge，禁止把全部线上坏例直接并入开发集；扩大人工双标样本校准 Judge，用加权 Kappa 与假通过率衡量。持久化指标和报警在多实例部署后再接。
- 新能力上线必须同时满足：固定评测集事实正确率不下降、答案完整性有明确提升、正确拒答率不明显下降、延迟增加在可接受范围、有超时/次数上限/日志/降级方案，且 `quality_gate.py` 通过。准确率和稳定性优先于小幅成本节省，但不接受没有评测收益的额外复杂度。
